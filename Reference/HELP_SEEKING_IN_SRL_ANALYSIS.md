## 1. 理論定位：Help-Seeking 在 SRL 中的位置

### 1.1 Pintrich (2000) SRL 四階段 × 四領域矩陣

SDL 平台的五階段方法論（定標→擇策→監評→調節→學習歷程）本質上是 Pintrich SRL 模型的教學實踐版。Help-Seeking 在這個矩陣中屬於**行為領域的資源管理策略**：

| SRL 階段 | 認知 | 動機/情感 | 行為 | 情境 |
|---------|------|----------|------|------|
| **前瞻/計畫** | 設定目標 | 自我效能評估 | 時間規劃 | 感知任務需求 |
| **監控** | 後設認知覺察 | 威脅感知評估 | **覺察需要幫助** | 監控同儕進度 |
| **控制** | 使用學習策略 | 調節動機 | **選擇求助策略** | 調整任務條件 |
| **反思** | 自我評價 | 歸因判斷 | **評估求助成效** | 評估環境支持 |

**關鍵洞察**：Help-Seeking 不是一個單點事件，而是貫穿 SRL 四個階段的**歷程**——從「覺察自己需要幫助」到「選擇向誰求助」到「評估幫助是否有效」。

### 1.2 Help-Seeking 在 SDL 五階段的對應

| SDL 階段 | SRL 對應 | Help-Seeking 的角色 |
|---------|---------|-------------------|
| **定標**（Goal Setting） | 前瞻/計畫 | 釐清目標時可能需要向教師確認方向（正式詢問 F-Query） |
| **擇策**（Strategy） | 前瞻/計畫 | **擇策的看板模板已包含「求助策略」欄位** — 學生需要事先規劃求助對象與方式 |
| **監評**（Monitoring） | 監控 + 控制 | 執行中遇到阻礙時的**實際求助行為**發生點 — 最關鍵的階段 |
| **調節**（Regulation） | 反思 | 回顧求助策略是否有效，調整未來的求助模式 |
| **學習歷程** | 反思（總結性） | 5Rs 反思中可回顧整體求助經驗 |

## 2. 平台現況盤點

### 2.1 與 Help-Seeking 直接相關的功能

#### A. AI Task Assistant（看板任務求助）— ⭐ 理論對齊度最高

**元件位置**：`sdl-frontend-main/src/components/AITaskAssistant/AITaskAssistantModal.jsx`
**資料模型**：`sdl-backend-main/models/help_seeking_log.js`

**運作流程**：

```
學生點擊任務卡片上的「求助」按鈕
         │
         ▼
┌─────────────────────────────────┐
│  Step 1: 後設認知狀態自評        │
│  ┌─ ○ 我還沒開始思考這個問題     │ ← 最低層級：尚未啟動認知
│  ├─ ○ 我想過但不確定方向        │ ← 已啟動但方向不明
│  ├─ ○ 我有初步想法，想確認可行性  │ ← 有假設，需驗證
│  ├─ ○ 我遇到具體的問題或障礙     │ ← 能具體定位困難點
│  └─ ○ 我問過同學/老師，想要第二意見│ ← 已用過其他來源（最高層級）
└─────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────┐
│  Step 2: 求助來源追蹤            │
│  ☐ 同學（Peers）               │ ← I-Query（非正式詢問）
│  ☐ 老師（Teacher）             │ ← F-Query（正式詢問）
│  ☐ 查資料（Resources）          │ ← S-Info（資訊檢索）
│  ☐ 還沒問任何人                 │ ← 首次求助入口
└─────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────┐
│  系統判定求助類型                 │
│  ┌─ adaptive（工具型）          │ ← 已嘗試思考 + 有明確問題
│  ├─ expedient（執行型）         │ ← 未思考 + 未問他人
│  └─ mixed（混合型）            │
└─────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────┐
│  AI 回應策略（依類型調整）        │
│  1. 思考方向提示（非答案）        │ ← 所有類型都提供
│  2. 建議諮詢的人際資源           │ ← 鼓勵回到社會互動
│  3. 詳細步驟（預設隱藏）         │ ← 需額外點擊，附帶警語
└─────────────────────────────────┘
```

**已捕捉的資料欄位**：

| 欄位 | 對應理論概念 |
|------|------------|
| `metacognitiveState` | Makara & Karabenick (2013) — 後設認知監控 |
| `helpSeekingType` (adaptive/expedient) | Nelson-Le Gall (1981) — 工具型 vs 執行型 |
| `askedSources` (JSON 陣列) | Cheng & Tsai (2011) — 求助來源分類 |
| `skippedThinking` (boolean) | 求助迴避/衝動行為指標 |
| `suggestions` (JSON) | AI 鷹架內容 |

#### B. 科學助手（Science Assistant）— 科學知識型 AI 求助

**元件位置**：`sdl-frontend-main/src/pages/Kanban/components/DraggableImage/components/ChatWindow.jsx`（`activeTab === 'science'`）
**資料模型**：`sdl-backend-main/models/rag_message.js`

**功能描述**：
- 基於 **RAGFlow 知識庫**回答科學探究與實作相關問題（附參考文獻引用）
- 可開啟 **Gemini Grounding + Google Search** 提供網路延伸閱讀連結
- 持久化會話管理（可建立多個對話、切換歷史記錄）
- 專案隔離（v2.0，每個專案的對話分開儲存）

**已捕捉的資料欄位**（`rag_messages` 表）：

| 欄位 | 說明 |
|------|------|
| `input_message` | 學生提出的問題 |
| `response_message` | AI 回答 |
| `reference_data` (JSONB) | RAGFlow 引用的參考文獻 |
| `external_links` (JSONB) | Gemini Grounding 外部連結 |
| `sessionId` | 會話 ID（對話歷程連續性） |
| `project_id` | 所屬專案 |

**Help-Seeking 角色**：
- 對應 **AI-Help**（向 AI 求助科學知識）
- 開啟延伸閱讀時同時對應 **S-Info**（資訊檢索），因為學生透過 AI 代為搜尋網路資源
- **缺少後設認知鷹架** — 學生可直接發問，無反思步驟，也無 adaptive/expedient 分類

#### D. KB Coach（想法牆 AI 教練）— 系統主動介入

**服務位置**：`sdl-backend-main/services/orchestrator.js`
**資料模型**：`sdl-backend-main/models/kb_coach_history.js`

| 偵測模式 | 觸發的 AI 人格 | 教學目的 |
|---------|--------------|---------|
| SHALLOW（淺層討論） | Idea Improver | 引導深入思考 |
| ECHO CHAMBER（回聲室） | Devil's Advocate | 挑戰團體迷思 |
| OVERLOAD（資訊過載） | Synthesizer | 整合發散想法 |

- 冷卻機制：至少 10 分鐘間隔、至少 5 則訊息門檻
- 這是**系統主動發起**的幫助，不同於學生主動的 Help-Seeking

#### E. 5Rs 反思系統 — 後設認知鷹架

**元件位置**：`sdl-frontend-main/src/components/FiveRsReflectionForm.jsx`

- Reporting → Responding → Relating → Reasoning → Reconstructing
- AI 逐層提供個人化回饋
- 與 Help-Seeking 的關係：反思是 SRL 的核心策略，學生在反思中可能揭露求助經驗

### 2.2 小組討論系統（非一般聊天室）

**重要澄清**：本平台的 Chatroom 是**專案範疇內的小組討論區**，不是一般的開放式聊天室。

**設計特徵**：

| 設計面向 | 實作方式 |
|---------|---------|
| **範疇** | 每個 Chatroom 綁定 `projectId`，僅小組成員可見 |
| **目的** | 支援小組內的學習討論與任務協調 |
| **定位** | SDL 學習流程中的**同儕互動管道** |
| **資料模型** | `chatroom_message` 表含 `projectId` 外鍵（NOT NULL） |
| **前端標題** | 「小組討論區」 |

**在 Help-Seeking 理論中的角色**：

小組討論區是 Cheng & Tsai (2011) 模型中 **I-Query（非正式詢問）** 的主要發生場域。學生在此向小組同儕提出問題、交換想法、協調任務分工。這與想法牆的討論功能互補：

| 管道 | 互動性質 | Help-Seeking 角色 |
|------|---------|------------------|
| **小組討論區** | 即時、自由形式的團隊對話 | 非正式同儕求助（I-Query）的主要管道 |
| **想法牆討論** | 錨定在特定節點上的脈絡化討論 | 針對特定概念的深度交流 |
| **AI Task Assistant** | 結構化、有後設認知鷹架的求助 | AI 輔助求助（AI-Help）+ 鼓勵回到同儕 |
| **科學助手** | 科學知識問答 + 網路延伸閱讀 | AI-Help + S-Info（代為搜尋），但缺乏求助分類 |
| **專案助理**（規劃中） | 尚未啟用，詳見[第 6 節設計構想](#6-專案助理設計構想未啟用功能) | — |

### 2.3 目前已捕捉的 Help-Seeking 行為數據

| 資料表 | 記錄什麼 | 能回答什麼研究問題 | 不能回答什麼 |
|-------|---------|------------------|------------|
| `help_seeking_log` | 後設認知狀態、求助來源、adaptive/expedient 分類 | 學生的求助類型分布？求助前嘗試了哪些來源？ | 求助後是否解決了問題？ |
| `rag_messages` | 學生問題、AI 回答、參考文獻、外部連結 | 學生問什麼科學問題？使用頻率？是否開啟延伸閱讀？ | **無求助類型分類，無法區分工具型 vs 執行型** |
| `chatroom_message` | 小組討論訊息 | 團隊溝通頻率？ | **無法區分閒聊 vs 求助** |

| `kb_coach_history` | AI 教練介入紀錄 | AI 介入的頻率與類型？ | 學生是否接受了建議？ |
| `ai_feedback` | helpful/not_helpful | AI 回應品質？ | 為什麼覺得沒幫助？ |
| `daily_personal` | 5Rs 反思內容 | 學生的後設認知發展？ | 未系統化挖掘求助相關反思 |

## 3. 理論對齊分析

### 3.1 Nelson-Le Gall (1981, 1985) 二分法

| 理論概念 | 平台實作 | 對齊程度 | 說明 |
|---------|---------|---------|------|
| **工具型求助 (Instrumental)** | ✅ AI Task Assistant 的 `adaptive` 分類 | 🟢 高 | 系統能判定並鼓勵工具型求助 |
| **執行型求助 (Executive)** | ✅ AI Task Assistant 的 `expedient` 分類 | 🟢 高 | 系統能判定並適度引導 |
| 工具型 vs 執行型的**跨通道追蹤** | ❌ 僅限 AI Task Assistant | 🔴 缺失 | 小組討論中的求助無分類 |

### 3.2 Karabenick (2004) 三分法

| 理論概念 | 平台實作 | 對齊程度 | 說明 |
|---------|---------|---------|------|
| **適應性求助 (Adaptive)** | ✅ 有判定機制 | 🟢 高 | — |
| **便宜行事型 (Expedient)** | ✅ 有判定機制 | 🟢 高 | — |
| **求助迴避 (Avoidance)** | ❌ 完全沒有偵測 | 🔴 缺失 | **最關鍵的缺口** — 詳見第 5 節 |

### 3.3 Makara & Karabenick (2013) 五維度模型

| 維度 | 平台實作 | 對齊程度 |
|------|---------|---------|
| **1. 威脅感知** (Threat Perception) | ❌ 未測量 | 🔴 缺失 |
| **2. 求助迴避** (Avoidance) | ❌ 未偵測 | 🔴 缺失 |
| **3. 求助來源** (Sources) | ✅ AI Task Assistant 追蹤 | 🟡 部分 |
| **4. 工具型求助** (Instrumental) | ✅ 有分類 | 🟢 高 |
| **5. 執行型求助** (Executive) | ✅ 有分類 | 🟢 高 |

### 3.4 Cheng & Tsai (2011) 線上求助來源分類

| 來源類型 | 平台對應管道 | 追蹤狀態 |
|---------|------------|---------|
| **S-Info（資訊檢索）** | 外部搜尋（Google 等） | ⚠️ 僅在 AI Task Assistant 的 `askedSources` 中以「查資料」選項記錄 |
| **F-Query（正式詢問）** | 向教師求助 | ⚠️ 同上，以「老師」選項記錄，但無追蹤實際互動 |
| **I-Query（非正式詢問）** | **小組討論區** + 想法牆討論 | ❌ 有管道但無法識別哪些訊息是求助 |
| **AI-Help（AI 輔助）** | AI Task Assistant + 科學助手 | ⚠️ Task Assistant 完整記錄；科學助手有記錄對話但無求助分類 |

### 3.5 Help-Seeking 行為編碼架構（你提供的二維架構）對照

#### 維度一：求助性質 (Function)

| 代碼 | 類別 | 平台能否偵測？ | 如何偵測？ |
|------|------|-------------|----------|
| **INS** | 工具型 | ✅ 在 AI Task Assistant 中可以 | `helpSeekingType === 'adaptive'` |
| **EXE** | 執行型 | ✅ 在 AI Task Assistant 中可以 | `helpSeekingType === 'expedient'` |
| **AVO** | 迴避型 | ❌ 完全無法偵測 | 需要交叉分析行為資料（詳見第 5 節） |

#### 維度二：求助來源 (Source)

| 代碼 | 類別 | 平台管道 | 追蹤狀態 |
|------|------|---------|---------|
| **S-Info** | 資訊檢索 | 外部（平台外） | ⚠️ 僅靠自陳報告 |
| **F-Query** | 正式詢問 | 教師（平台外居多） | ⚠️ 僅靠自陳報告 |
| **I-Query** | 非正式詢問 | **小組討論區 + 想法牆** | ❌ 有管道但無標記 |
| **AI-Help** | AI 輔助 | AI Task Assistant + 科學助手 | ⚠️ Task Assistant 完整；科學助手有對話紀錄但無分類 |

## 4. 關鍵缺口與建議

### 缺口 1：求助迴避偵測（最高優先 — 詳見第 5 節）

**理論依據**：Won (2024) 發現求助迴避**正向預測混亂學習行為**、**負向預測 STEM 留任意圖**。在 Karabenick 三分法中，迴避型是最具破壞力的模式。

**現況**：平台完全無法識別「需要幫助但不求助」的學生。

**建議**：建立行為交叉分析的求助迴避偵測系統（詳見第 5 節完整設計）。

### 缺口 2：教師端缺乏 Help-Seeking 分析儀表板

**理論依據**：Help-Seeking 是 SRL 的資源管理策略。教師作為學習的促進者，需要掌握學生的策略使用狀態才能做適性介入。

**現況**：Teacher Dashboard（`teacher-dashboard/components/AnalyticsView.jsx`）目前只有活動量指標（節點數、任務完成數、反思數量），完全沒有 Help-Seeking 相關指標。

**建議新增的儀表板模組**：

```
┌────────────────────────────────────────────────┐
│  Help-Seeking 分析面板                          │
│                                                │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐     │
│  │ 求助頻率  │  │ 類型分布  │  │ 迴避預警  │     │
│  │  12 次   │  │ 70% 適應 │  │ ⚠️ 2 人   │     │
│  └──────────┘  └──────────┘  └──────────┘     │
│                                                │
│  📊 各學生求助行為概覽                           │
│  ┌─────────┬──────┬──────┬──────┬──────┐      │
│  │  學生    │ AI求助│ 同儕 │ 類型  │ 風險  │      │
│  ├─────────┼──────┼──────┼──────┼──────┤      │
│  │ 學生 A  │  5次  │ 高   │ 適應  │ 🟢   │      │
│  │ 學生 B  │  0次  │ 低   │  —   │ 🔴   │      │
│  │ 學生 C  │  8次  │ 低   │ 執行  │ 🟡   │      │
│  └─────────┴──────┴──────┴──────┴──────┘      │
│                                                │
│  📈 求助頻率時間軸（折線圖）                      │
│  📊 Adaptive vs Expedient 趨勢（堆疊圖）         │
│  🕸️ 求助來源偏好（雷達圖）                       │
└────────────────────────────────────────────────┘
```

**資料來源**：已存在的 `help_seeking_log`、`chat_turn`、`ai_feedback` 表，可直接查詢，無需新增資料表。

### 缺口 3：求助成效追蹤不完整

**理論依據**：SRL 的反思階段要求學習者評估策略的有效性。如果學生不知道自己的求助是否有效，就無法改善求助品質。

**現況**：只有 `ai_feedback` 的二元評分 (helpful/not_helpful)，缺乏行為層面的成效追蹤。

**建議**：在 `help_seeking_log` 中新增成效追蹤欄位：

| 新欄位 | 說明 | 如何取得 |
|-------|------|---------|
| `task_status_before` | 求助前任務狀態 | 系統自動記錄 |
| `task_status_after_24h` | 求助後 24 小時任務狀態 | 排程任務自動檢查 |
| `repeated_help_count` | 同一任務的重複求助次數 | 系統計算 |
| `self_rated_resolution` | 學生自評問題是否解決 (1-5) | 求助後跳出輕量評分 |

### 缺口 4：小組討論中的求助行為不可見

**理論依據**：同儕是學生最常使用的求助來源 (Li, 2023)。如果平台無法辨識小組討論中的求助行為，等於遺失了最大量的求助數據。

**現況**：`chatroom_message` 只記錄訊息內容、作者、專案 ID。無法區分「任務協調」、「閒聊」和「求助」。

**建議（輕量方案）**：

不強制分類，而是提供**可選標記**：

```
┌─────────────────────────────────────┐
│  小組討論區                          │
│                                     │
│  [王小明] 14:32                      │
│  這個部分我卡住了，有人知道怎麼      │
│  做嗎？ 🏷️ #求助                    │
│                                     │
│  [李小華] 14:35                      │
│  你可以試試看用這個方法... ✅ 已回答   │
│                                     │
│  ─────────────────────────          │
│  輸入訊息...  [🏷️ 標記求助] [送出]   │
└─────────────────────────────────────┘
```

- 訊息送出時可選擇「標記為求助」
- 他人可回覆「已回答」標記
- 系統追蹤求助→回答的閉環

### 缺口 5：缺乏「專案層級」的 AI 求助管道

**理論依據**：AI Task Assistant 的鷹架設計僅限於**單一任務**層級。但學生在 SRL 歷程中也會遇到**專案層級**的困難（例如：整體方向不確定、階段轉換的困惑、跨任務的概念整合問題），這類問題無法用單一任務的求助框架處理。

**現況**：專案助理（Project Assistant）的前端 UI 已存在但被註解掉，功能尚未完成。目前學生缺乏一個能處理專案層級問題的結構化 AI 求助管道。

**影響**：這意味著學生在遇到跨任務或策略層級的困難時，只能透過小組討論（I-Query）或直接找老師（F-Query），AI-Help 管道在這個層級是缺位的。

**設計構想**：詳見[第 6 節](#6-專案助理設計構想未啟用功能)。

## 5. 求助迴避偵測機制（詳細設計）

### 5.1 為什麼這是最關鍵的功能？

在你的文獻框架中：

- **Won (2024)**：求助迴避**正向預測混亂學習行為**，**負向預測 STEM 留任意圖**
- **Karabenick (2004)**：將求助迴避獨立為第三類別，因為它的破壞力超過執行型求助
- **Makara & Karabenick (2013)**：威脅感知 → 求助迴避 是最需要介入的路徑

> **核心問題**：AI Task Assistant 只能服務「已經開口求助」的學生。但研究告訴我們，最需要幫助的學生往往是**那些從不出現在 `help_seeking_log` 裡的人**。

### 5.2 使用情境考量（關鍵設計約束）

**實際使用模式**：目前一個班級每週 2 堂課（約 90-100 分鐘），課後是否使用不確定。

這意味著偵測邏輯**不能用絕對的日曆時間**作為門檻。如果用「任務停滯 > 24 小時」來判定，幾乎所有學生在兩堂課之間都會被誤判。因此，偵測必須基於以下原則：

| 原則 | 說明 | 錯誤做法 | 正確做法 |
|------|------|---------|---------|
| **以「課堂」為分析單位** | 行為比較應在同一堂課的時段內進行 | 「48 小時內無求助」 | 「連續 2 堂課內無求助」 |
| **與同儕相對比較** | 不看絕對數值，看與同班/同組的相對差異 | 「發言 < 3 則」 | 「發言低於小組平均 50%」 |
| **跨課堂累積** | 單堂課的數據不足以判定，需要跨 2-3 堂課的趨勢 | 一堂課沒發言 = 迴避 | 連續 2 堂課沒發言 + 有困難信號 = 可能迴避 |
| **可配置的時間框架** | 不同課程設定需要不同參數 | 寫死 24h / 48h | 教師可設定「每週上課次數」和「是否有課後作業」 |

**不同部署情境的參數化設計**：

```
使用情境設定（教師/管理者可配置）：

┌─────────────────────────────────────────────────────┐
│  課程使用模式設定                                      │
│                                                      │
│  每週上課次數:  [2] 堂                                │
│  每堂課時長:    [45] 分鐘                             │
│  是否有課後任務: [○ 是 ● 否]                          │
│  階段週期:      [2] 週                               │
│                                                      │
│  → 系統自動推算：                                     │
│    分析窗口 = 2 堂課 = 1 週                           │
│    困難判定 = 跨 2 堂課趨勢                            │
│    預警觸發 = 在下一堂課前（教師可提前介入）             │
└─────────────────────────────────────────────────────┘

未來如果上架到不同情境，只需調整上方設定：
- 每日使用課程 → 分析窗口縮短為 2-3 天
- 自主線上學習 → 分析窗口改為「最近 N 次活躍 session」
- 密集工作坊   → 分析窗口改為數小時
```

### 5.3 偵測邏輯：兩層偵測架構

根據使用情境，偵測分為**課堂內即時偵測**和**跨課堂趨勢偵測**兩層：

#### 第一層：課堂內即時偵測（In-Session Detection）

在學生實際使用平台的時段內進行，分析單位是**分鐘**：

| 信號 | 判定邏輯 | 說明 |
|------|---------|------|
| **任務瀏覽但無動作** | 學生打開任務卡片 > 3 次但未編輯、未求助、未移動 | 可能在反覆查看但不知道怎麼開始 |
| **欄位阻塞無後續** | 任務被移到 Blocked 欄位後，同一堂課內未發起任何求助 | 學生自認卡住了但沒有行動 |
| **AI 助手打開但未送出** | 打開 AI Task Assistant modal 但關閉未送出問題 | 可能猶豫是否該求助（威脅感知） |
| **同儕都在互動但該生沈默** | 同一堂課中，小組其他成員有發言/編輯，但該生 > 20 分鐘無任何操作 | 相對於同儕的沈默 |

**觸發時機**：課堂進行中，即時顯示柔性提示。

#### 第二層：跨課堂趨勢偵測（Cross-Session Trend Detection）

在課堂結束後進行分析，分析單位是**堂**：

| 信號 | 判定邏輯 | 說明 |
|------|---------|------|
| **連續無進展** | 過去 2 堂課中，該生被分配的任務均無狀態變更 | 跨課堂的停滯趨勢 |
| **求助頻率趨零** | 之前有使用 AI 求助或小組討論，但最近 2 堂課完全停止 | 行為模式的突然變化比絕對數值更重要 |
| **反思品質下降趨勢** | 5Rs 反思從之前寫到 Reasoning/Reconstructing，最近只寫 Reporting | 後設認知投入的退縮 |
| **截止壓力 + 低完成率** | 階段即將結束，但該生的任務完成率明顯低於小組平均 | 配合教學進度的時間壓力 |

**觸發時機**：每堂課後或每週排程計算，結果在教師儀表板上呈現（教師下一堂課前可查看）。

#### 交叉判定矩陣（不變，但時間語意改變）

```
                    │  有使用求助管道   │  沒有使用求助管道
────────────────────┼────────────────┼─────────────────
 有困難跡象          │  正常求助行為    │  ⚠️ 可能在迴避求助
                    │  （系統運作正常） │  （需要介入）
────────────────────┼────────────────┼─────────────────
 沒有困難跡象        │  可能是主動學習  │  正常獨立學習
                    │  或執行型求助    │  （無需擔心）
────────────────────┴────────────────┴─────────────────
```

**只有右上象限（有困難跡象 + 沒有使用求助管道）才觸發迴避預警。**

### 5.4 風險分級（基於課堂次數，非小時數）

```
🟢 綠燈（Low Risk）
   條件：最近 2 堂課中，困難信號 ≤ 1 個，或有困難但有使用任一求助管道
   動作：無

🟡 黃燈（Medium Risk）
   條件：最近 2 堂課中，2 個以上困難信號 + 期間無任何求助行為
   動作：
   - 【課堂內】在該生下次登入時，任務卡片上顯示柔性提示
   - 【教師端】在儀表板預警清單中標記為黃燈
   - 【時機】下一堂課前讓教師可以查看

🔴 紅燈（High Risk）
   條件：連續 3 堂課（或 1.5 週）中，困難信號持續存在 + 無求助行為 + 有截止壓力
   動作：
   - 【教師端】發出預警通知 + 提供情境摘要
   - 【課堂內】如偵測到學生在線，顯示更明確的柔性提示
   - 【建議】教師下一堂課優先私下關心該生
```

### 5.5 「柔性提示」設計原則

**絕對不能做的事**：
- ❌ 跳出強制彈窗要求學生求助 — 這會加重威脅感
- ❌ 公開顯示迴避標記 — 社交壓力會適得其反
- ❌ 自動替學生求助 — 違反 SRL 的自主性原則

**應該做的事**：
- ✅ **降低求助門檻** — 在任務卡片旁邊顯示不顯眼的提示
- ✅ **正常化求助行為** — 「你的小組有 3 位同學也在這個任務上尋求了幫助」
- ✅ **提供多種管道選擇** — 不是只推 AI，也建議找同學或老師
- ✅ **連結到求助策略** — 提醒學生在「擇策」階段規劃的求助策略

```
柔性提示範例（嵌入任務卡片底部，非彈窗）：

課堂內即時提示（偵測到 20 分鐘無動作 + 任務在 Blocked）：
┌─────────────────────────────────────────┐
│  📌 任務：完成文獻回顧整理              │
│  狀態：阻塞中                           │
│                                         │
│  ┌─────────────────────────────────┐    │
│  │ 💬 需要幫忙嗎？                  │    │
│  │                                 │    │
│  │ [問問 AI 助手]  [找同學聊聊]     │    │
│  │ [先不用，謝謝]                   │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘

跨課堂趨勢提示（上堂課後計算，下次登入時顯示）：
┌─────────────────────────────────────────┐
│  📋 你有 2 個任務上堂課就在進行中了，     │
│     需要一些幫助嗎？                     │
│                                         │
│  [查看任務]  [問問 AI 助手]  [不用了]    │
└─────────────────────────────────────────┘
```

**如果學生選擇「先不用，謝謝」**：記錄這個選擇（這本身就是有價值的數據——「有意識地拒絕幫助」與「不知道可以求助」是不同的），且一段時間內不再重複提示。

### 5.6 教師端的介入支持

教師看到紅燈/黃燈預警後，系統應提供**情境摘要**而非只是名字。注意語言使用「堂課」而非「天數」作為時間單位：

```
⚠️ 學生 B 可能需要關注

困難信號（過去 2 堂課）：
• 任務「資料分析」連續 2 堂課未有任何更新
• 本週 2 堂課中小組討論發言 0 則（小組平均 6 則）
• 最近一次 5Rs 反思只寫了 Reporting 層（之前通常寫到 Reasoning）

求助紀錄：
• 最後一次使用 AI 助手：上上堂課（2/4）
• 上堂課有打開 AI 助手但未送出問題

建議介入方式：
• 下堂課私下關心，避免在小組面前提及
• 可以從最近的反思內容切入對話
• 協助釐清目前的卡關點
```

### 5.7 技術實作概要

偵測分兩個運算時機：

**A. 課堂內即時偵測（前端 + Socket.IO）**

```
運作方式：前端埋點 + 後端即時判定

前端追蹤事件（透過 Socket.IO emit）：
- task:viewed       → 學生打開任務卡片
- task:edited       → 學生編輯任務內容
- aiAssistant:opened → 學生打開 AI 助手 modal
- aiAssistant:closed → 學生關閉 AI 助手（未送出 = 可能猶豫）
- chatroom:message  → 學生在小組討論發言

後端判定邏輯（socketManager 或 dedicated handler）：
- 維護每個學生的 session 狀態（記憶體中，不存 DB）
- 當觸發柔性提示條件時，emit 事件到該學生的 socket
- 柔性提示在該堂課中最多出現 1 次（避免干擾）
```

**B. 跨課堂趨勢偵測（排程任務）**

```
觸發時機：每堂課結束後自動執行（或教師手動觸發）

排程任務流程：

1. 讀取課程設定（每週上課次數、堂數、是否有課後作業）
2. 定義分析窗口 = 最近 N 堂課（預設 N=2）
3. 對每位學生計算：

   a. 困難信號分數 = Σ(各信號權重)
      - 連續 N 堂課任務無進展:           +3 分
      - 任務在 Blocked 欄且未處理:        +3 分
      - 反思品質下降（與自己之前比）:       +2 分
      - 在線時間足夠但無產出:             +1 分
      - 階段截止壓力（< 1 週）:           +2 分

   b. 求助活躍度分數 = 分析窗口內
      - AI Task Assistant 使用次數
      - 科學助手對話次數（rag_messages）
      - 小組討論發言次數（與小組平均比）
      - 想法牆互動次數

   c. 行為突變偵測
      - 之前活躍但最近突然沈默:            +2 分（加權）

4. 風險判定：
   if 困難信號 >= 4 AND 求助活躍度 == 0:
       風險 = 🔴 紅燈
   elif 困難信號 >= 2 AND 求助活躍度 <= 1:
       風險 = 🟡 黃燈
   else:
       風險 = 🟢 綠燈

5. 結果寫入 help_seeking_risk 表
6. 教師儀表板讀取此表（下堂課前可查看）
```

### 5.8 這與你的文獻框架的對應

| 理論概念 | 偵測機制的對應 |
|---------|-------------|
| **Cornally & McCarthy (2011) — 求助是「針對問題的」** | 偵測先確認「是否存在問題」（困難信號），再看「是否有求助行為」 |
| **Karabenick (2004) — 求助迴避是獨立類別** | 獨立追蹤迴避行為，而非只追蹤「有求助」的學生 |
| **Makara & Karabenick (2013) — 威脅感知 → 迴避** | 柔性提示設計降低威脅感，教師介入建議強調私下、非評價性 |
| **Won (2024) — 迴避預測混亂行為** | 紅燈預警的目的就是在「混亂行為」出現之前介入 |
| **Nelson-Le Gall (1985) — 求助是一種技能** | 提示設計包含「引導學生怎麼求助」，而非只是推他去求助 |

## 6. 專案助理設計構想（未啟用功能）

### 6.1 現況

專案助理（Project Assistant）的前端 UI 已存在於 `ChatWindow.jsx` 中（`activeTab === 'project-assistant'`），但被註解掉。後端的 `useAssistantChat.js`、`streamingService.js`、`orchestrator.js` 已有 RAG + Streaming 的基礎架構。功能尚未完成，定位與設計方向待釐清。

### 6.2 定位思考：它應該解決什麼問題？

目前平台的 AI 求助管道是 **AI Task Assistant**，它專注在**單一任務層級**。但學生在 SRL 歷程中會遇到不同層級的困難：

```
┌─────────────────────────────────────────────┐
│  層級 3：學習策略與後設認知                     │
│  「我不知道我的學習方法有沒有效」                │
│  「我覺得整個方向不對但說不出為什麼」             │
│  → 目前無 AI 管道                             │
├─────────────────────────────────────────────┤
│  層級 2：專案/階段層級                         │
│  「定標和擇策的差別我搞不清楚」                  │
│  「我們小組的研究問題是不是太大了？」              │
│  → 目前無 AI 管道                             │
├─────────────────────────────────────────────┤
│  層級 1：單一任務層級                          │
│  「這個任務我不知道怎麼開始」                    │
│  → ✅ AI Task Assistant 已覆蓋                │
└─────────────────────────────────────────────┘
```

**專案助理可以填補層級 2 和層級 3 的空缺。**

### 6.3 設計方向：三種可能的定位

#### 方向 A：階段導航員（Stage Navigator）

**核心概念**：專注於引導學生理解和推進 SDL 五階段流程。

```
運作方式：
- 知道學生目前在哪個階段、完成了哪些必填欄位
- 幫助學生理解「為什麼要做這個階段」
- 在階段轉換時提供過渡指引
- 不處理具體任務內容，而是處理「我現在該做什麼」

適合場景：
- 「我們小組做完定標了，擇策要做什麼？」
- 「成功標準要怎麼寫？」
- 「監評階段的 Blocked 欄位是什麼意思？」
```

**與 Help-Seeking 的關係**：這是 S-Info（資訊檢索）的 AI 版本。學生不是在求助「怎麼解決問題」，而是在查詢「流程本身的規則」。

#### 方向 B：SRL 教練（SRL Coach）

**核心概念**：基於學生的行為數據，主動引導 SRL 策略使用，包含 Help-Seeking 策略。

```
運作方式：
- 讀取學生的學習行為數據（任務完成率、反思品質、求助紀錄）
- 提出後設認知問題：「你覺得上週的學習策略有效嗎？」
- 連結到擇策階段的計畫：「你在擇策時規劃了找老師問 X，後來有問嗎？」
- 幫助學生反思自己的求助行為模式

適合場景：
- 「我覺得學習卡住了但不知道問題在哪」
- 「我要怎麼改善我的學習方法？」
- 系統偵測到求助迴避時，作為柔性介入的管道
```

**與 Help-Seeking 的關係**：這直接對應了 Karabenick & Gonida (2018) 的定義——將 Help-Seeking 作為 SRL 策略來教學。AI 不只回答問題，而是**教學生如何成為更好的求助者**。

#### 方向 C：RAG 式專案顧問（Project Advisor）

**核心概念**：利用已有的 RAG 架構，讓 AI 理解整個專案的上下文後提供建議。

```
運作方式：
- 自動注入專案資料（看板任務、想法牆、提交紀錄、對話歷史）
- 分析專案整體進度與品質
- 提供跨任務的建議：「你的文獻回顧和研究問題之間似乎有落差」
- 識別專案風險：「你們的時間規劃可能太樂觀了」

適合場景：
- 「幫我看看我們專案整體有什麼問題」
- 「我們的研究方向是否合理？」
```

**與 Help-Seeking 的關係**：這是傳統的 AI-Help 管道，但層級從「任務」提升到「專案」。

### 6.4 我的建議：方向 B（SRL 教練）優先

**理由**：

1. **理論獨特性**：方向 A 和 C 在其他教育平台上已有類似實作（課程引導 chatbot、專案管理 AI）。但**將 Help-Seeking 策略的培養嵌入 AI 對話**，在文獻中幾乎沒有被實作過——你的文獻框架中也指出 AI/Chatbot 作為求助對象是「極少研究」的新興領域。

2. **數據已具備**：你的平台已經有 `help_seeking_log`（求助紀錄）、`daily_personal`（反思）、任務進度等數據。SRL 教練可以直接利用這些數據做個人化引導，不需要額外建設。

3. **填補迴避偵測的「後端」**：第 5 節的求助迴避偵測是「發現問題」，而 SRL 教練可以是「解決問題」——當系統偵測到學生可能在迴避求助時，SRL 教練可以用對話的方式引導學生反思自己的求助行為。

4. **可與方向 A、C 漸進整合**：SRL 教練可以在對話中自然地融入階段導航和專案分析，不需要一開始就建構完整的 RAG 管道。

### 6.5 如果用方向 B，後設認知鷹架的設計

專案助理作為 SRL 教練，每次開啟對話時的流程：

```
┌─────────────────────────────────────────────┐
│  SRL 教練                                    │
│                                              │
│  你好 [學生名字]，今天想聊什麼？               │
│                                              │
│  ┌─────────────────────────────────────┐     │
│  │  [📋 專案進度]  我想了解目前的狀況    │     │  ← 階段導航功能
│  │  [🤔 學習反思]  我想回顧學習策略      │     │  ← SRL 教練核心
│  │  [❓ 我有問題]  我遇到困難想求助      │     │  ← 轉接到求助流程
│  │  [💬 自由對話]  其他                 │     │  ← 開放式
│  └─────────────────────────────────────┘     │
│                                              │
│  如果選擇「我有問題」：                        │
│  → 觸發類似 AI Task Assistant 的後設認知提問    │
│  → 記錄到 help_seeking_log                    │
│  → 如果問題屬於單一任務，建議使用 Task Assistant │
│                                              │
│  如果選擇「學習反思」：                        │
│  → AI 基於近期數據提出引導問題：               │
│     「我注意到你這週在 [任務 X] 上花了比較多    │
│      時間。你覺得遇到了什麼困難嗎？」           │
│     「你在擇策時規劃了 [策略 Y]，                │
│      實際執行下來感覺如何？」                   │
└─────────────────────────────────────────────┘
```

**關鍵設計原則**：
- 選擇「我有問題」時，走與 AI Task Assistant 一致的後設認知流程，記錄到同一張 `help_seeking_log` 表
- 選擇「學習反思」時，AI 主動調出學生的行為數據進行引導式對話
- 所有對話都記錄 `chat_turn`，標記 `source: 'project-assistant'` 以便區分管道

## 7. 實作優先順序

### 第一優先：奠定 Help-Seeking 分析基礎

| 項目 | 內容 | 理由 |
|------|------|------|
| **A. 教師 Help-Seeking 儀表板** | 利用已有的 `help_seeking_log` 資料，新增分析視圖 | 數據已存在，只需要前端展示。教師是介入的關鍵角色。 |
| **B. 求助迴避偵測 v1** | 實作排程任務 + 風險分級 + 教師端預警清單 | 填補最大的理論缺口。不需要複雜的 ML，簡單的規則引擎即可。 |
| **C. 求助成效追蹤** | 在 `help_seeking_log` 新增 `task_status_before`、`task_status_after_24h` 欄位 | 讓 SRL 的反思階段有數據支撐。 |

### 第二優先：擴展追蹤覆蓋面

| 項目 | 內容 | 理由 |
|------|------|------|
| **D. 小組討論求助標記** | 可選的 `#求助` 標記 + 「已回答」標記 | 讓 I-Query（非正式同儕求助）可追蹤，覆蓋最常用的求助管道。 |
| **E. 統一 Help-Seeking 事件模型** | 建立 `help_seeking_event` 表，統一各管道的求助紀錄 | 為跨管道分析和研究輸出打基礎。 |

### 第三優先：進階功能（長期）

| 項目 | 內容 | 理由 |
|------|------|------|
| **F. 專案助理（SRL 教練）** | 以方向 B 為基礎設計，整合後設認知鷹架與行為數據引導 | 填補專案層級的 AI 求助空缺，同時培養求助技能。 |
| **G. 自適應求助鷹架** | 漸進式幫助：提示 → 解釋 → 步驟 → 人際轉介 | 強化工具型求助的「最小量提示」原則。 |
| **H. 求助網絡社會圖譜** | 分析「誰幫助誰」的社交網絡 | 識別孤立學生和知識橋梁。 |
| **I. 縱貫性分析** | 追蹤學生求助策略隨時間的變化 | 驗證平台是否成功培養了適應性求助技能。 |
