# Postmortem 事後檢討

## 概述

此 skill 提供事件事後檢討指引，從事件中學習並預防再次發生。

## 適用角色

| 角色 | 職責 |
|------|------|
| **主持人** | Engineering Manager |
| **參與者** | 相關工程師、利害關係人 |

---

## 1. 核心原則

- **不責怪個人** (Blameless)
- 聚焦系統改善
- 透明公開
- 持續追蹤改善項目

---

## 2. Postmortem 模板

```markdown
# Postmortem: [事件標題]

## 事件摘要
- **日期**: 2024-01-20
- **持續時間**: 75 分鐘
- **嚴重度**: SEV1
- **影響**: 全部用戶無法登入

## 時間軸 (UTC)

| 時間 | 事件 |
|------|------|
| 14:30 | 監控告警觸發 |
| 14:35 | On-call 開始調查 |
| 14:45 | 確認資料庫連線池耗盡 |
| 15:00 | 增加連線池大小並重啟 |
| 15:15 | 服務恢復 |
| 15:45 | 全面驗證完成 |

## 根本原因

資料庫連線池大小設定過小（20），在流量高峰時無法滿足需求。
部署新版本後 API 並發增加，導致連線池耗盡。

## 影響

- **用戶影響**: 100% 用戶 75 分鐘無法使用
- **業務影響**: 預估損失 $XX,XXX
- **聲譽影響**: 社群媒體負面反饋

## 做得好的地方

- 告警及時觸發
- On-call 快速回應
- 團隊協作順暢
- 回滾決策果斷

## 需要改善的地方

- 連線池監控不足
- 部署前負載測試不完整
- 缺少自動擴容機制

## 改善項目

| 項目 | 優先級 | 負責人 | 截止日 |
|------|--------|--------|--------|
| 增加連線池監控 | P0 | @devops | 2024-01-25 |
| 加入自動擴容 | P1 | @backend | 2024-02-01 |
| 更新負載測試流程 | P1 | @qa | 2024-02-01 |
| 更新 Runbook | P2 | @sre | 2024-01-30 |

## 預防措施

1. 所有部署前必須通過負載測試
2. 關鍵資源加入飽和度監控
3. 季度容量規劃審查
```

---

## 3. Postmortem 流程

```
事件結束 → 48hr 內 → 撰寫草稿 → 團隊審查 → 發布 → 追蹤改善
```

### 會議議程 (1 小時)

| 時間 | 議題 |
|------|------|
| 5 min | 開場、提醒 Blameless |
| 15 min | 時間軸回顧 |
| 15 min | 根因分析 |
| 15 min | 改善項目討論 |
| 10 min | 優先級排序、分配 |

---

## 4. 根因分析方法

### 5 Whys

```
問題：用戶無法登入

1. Why? → API 回傳 500 錯誤
2. Why? → 資料庫連線逾時
3. Why? → 連線池耗盡
4. Why? → 連線池太小
5. Why? → 容量規劃未考慮新功能
```

---

## 5. 改善項目追蹤

- 建立 Jira/GitHub Issue
- 加入 Sprint backlog
- 每月審查進度

---

## 檢查清單

- [ ] 48 小時內安排會議
- [ ] 邀請所有相關人員
- [ ] 草稿已撰寫
- [ ] 改善項目已建立追蹤
- [ ] Postmortem 已發布
