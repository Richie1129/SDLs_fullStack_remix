# 架構決策記錄 (Architecture Decision Record)

## 概述
此 skill 協助撰寫架構決策記錄 (ADR)，用於記錄軟體架構中的重要技術決策、決策背景、考慮的選項、最終選擇及其理由，確保團隊對技術決策有共同理解並可追溯。

## 適用角色
- **主要負責**: 系統架構師、技術主管、資深工程師
- **協作角色**: 開發團隊、產品經理、DevOps 工程師

## 輸入需求
使用者需要提供：
- 需要決策的技術問題
- 業務背景和需求
- 已考慮的替代方案
- 技術限制和約束
- 相關利害關係人意見

範例：`請幫我撰寫選擇資料庫技術的 ADR，我們在考慮 PostgreSQL vs MongoDB`

## 執行步驟

### 步驟 1: 理解決策背景
- 釐清需要決策的問題
- 了解業務需求和驅動因素
- 識別技術約束

### 步驟 2: 評估選項
- 列出可行的替代方案
- 分析各方案的優缺點
- 考慮長期影響

### 步驟 3: 做出決策
- 選擇最適合的方案
- 記錄決策理由
- 說明預期影響

### 步驟 4: 撰寫 ADR
- 使用標準模板
- 清晰描述背景和決策
- 記錄後果和影響

### 步驟 5: 審核與存檔
- 團隊審核
- 版本控制
- 建立索引

## ADR 命名與管理規範

### 命名規則
- 格式: `ADR-[編號]-[簡短標題].md`
- 範例: `ADR-001-database-selection.md`
- 編號: 三位數字，從 001 開始

### 狀態定義
| 狀態 | 說明 |
|------|------|
| 提議中 (Proposed) | 正在討論中，尚未決定 |
| 已接受 (Accepted) | 決策已通過，準備實施 |
| 已棄用 (Deprecated) | 不再適用，但保留參考 |
| 已取代 (Superseded) | 被新的 ADR 取代 |

### 索引範例
```markdown
# ADR 索引

| 編號 | 標題 | 狀態 | 日期 |
|------|------|------|------|
| 001 | 選擇 PostgreSQL 作為主資料庫 | 已接受 | 2024-01-15 |
| 002 | 採用 Docker 容器化部署 | 已接受 | 2024-01-20 |
| 003 | 使用 REST API 而非 GraphQL | 已接受 | 2024-02-01 |
| 004 | 前端框架選擇 React | 已接受 | 2024-02-05 |
```

## 範例: 完整 ADR

### ADR-001: 選擇 PostgreSQL 作為主資料庫

**狀態**: 已接受
**日期**: 2024-01-15
**決策者**: 技術長 王小明
**審核者**: 架構師 李大華

---

**背景**:
我們的電商平台需要儲存用戶資料、商品資訊和訂單交易。
預計第一年達到 10 萬用戶，每日 5 萬筆訂單。
需要 ACID 保證確保訂單資料完整性。

**決策**:
我們決定採用 PostgreSQL 作為主資料庫。

**選項評估**:
1. PostgreSQL - 開源、ACID、JSON 支援
2. MySQL - 開源、廣泛使用
3. MongoDB - 文件型、彈性 Schema

**決策理由**:
1. 訂單系統需要 ACID 保證
2. 團隊有 SQL 經驗
3. JSONB 支援兼顧彈性
4. AWS RDS 支援，維運簡單

**後果**:
- ✅ 資料一致性有保障
- ✅ 開發團隊可快速上手
- ⚠️ 需要注意連線池管理
- ⚠️ 大規模時需考慮分庫分表
