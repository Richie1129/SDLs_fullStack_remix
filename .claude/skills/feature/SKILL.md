# Feature 實作確認 Skill

當使用者執行 `/feature` 時，在動手寫程式碼之前，先完成確認流程。

## 使用方式
```
/feature <功能描述>
```

範例：
```
/feature 新增範例任務對話框，讓學生可以預填選取任務類型
/feature 在看板新增任務類型篩選器
```

## 執行步驟

### 步驟 1：探索相關程式碼

根據功能描述，快速掃描相關檔案：
- 找出最可能需要修改的 2-5 個檔案
- 確認現有的相關元件或 hooks
- 檢查是否有類似的實作可以參考

```bash
# 範例：搜尋相關元件
grep -r "關鍵字" sdl-frontend-main/src --include="*.jsx" -l
```

### 步驟 2：確認套件可用性

若功能需要特定套件，先確認是否已安裝：
```bash
cat sdl-frontend-main/package.json | grep "dependencies" -A 50
# 或
cat sdl-backend-main/package.json | grep "dependencies" -A 50
```

**若套件未安裝，先告知使用者，詢問是否要安裝，不要自行假設可用。**

### 步驟 3：產出確認清單

以下格式呈現，等待使用者確認後再動手：

```
## 功能確認：<功能名稱>

### 互動模型
- 觸發方式：<使用者如何啟動這個功能？>
- 預期行為：<每個操作步驟發生什麼？>
- 完成狀態：<成功後畫面呈現什麼？>

### 需要釐清的問題（若有）
1. <問題一>：選項 A _____ 或 選項 B _____？
2. <問題二>：...

### 計劃修改的檔案
1. `路徑/檔案.jsx` — 說明要做什麼改動
2. `路徑/檔案.js` — 說明要做什麼改動
（最多列 5 個，更多的說明「及其他 N 個檔案」）

### 套件狀態
- `套件名稱`: ✅ 已安裝 / ❌ 需要安裝

### 完成條件
- [ ] <可驗證的完成標準一>
- [ ] <可驗證的完成標準二>
```

### 步驟 4：等待確認

**在使用者明確確認（「好」、「可以」、「開始做」）之前，不要開始寫任何程式碼。**

若使用者提出修改，更新確認清單後再次確認。

### 步驟 5：實作

確認後依計劃執行，完成後對照完成條件逐一驗證。

## 注意事項
- 若功能描述清晰且無歧義，可以簡化確認清單，但互動模型必須明確
- 若使用者在 `/feature` 後附帶詳細說明（如按鈕文字、每步操作），直接採用，不需再問
- 完成後主動說明修改了哪些檔案、每個檔案做了什麼改動
