## 執行摘要

### 問題陳述
v2.2 實作了「完整階段結構」，讓 AI 能看到所有階段/子階段的定義，但存在關鍵缺陷：

1. **提交記錄不完整**：只顯示最近 5 條提交，無法判斷所有階段的完成狀況
2. **資料結構分離**：階段結構與提交記錄是兩個獨立物件，AI 需自行解析對應關係
3. **欄位完整性不可見**：無法判斷每個子階段的「需填寫欄位」是否完整填寫

### 解決方案
新增「階段完成狀態」資料結構，整合階段定義與提交記錄，讓 AI 能夠：
- 看到每個子階段的提交狀態（已提交/未提交）
- 知道每個提交是否完整（哪些欄位已填，哪些遺漏）
- 計算每個階段的完成度百分比
- 精確判斷專案進度和遺漏項目

### 關鍵指標
- **實作複雜度**: 1 個新函數 + 1 個新欄位 + Prompt 更新
- **破壞性**: 0（完全向後相容）
- **效能影響**: +1 次資料庫查詢（與其他查詢並行）
- **Token 增加**: 預估 +1500-2000 tokens（全量預載策略）

## 問題分析（Linus 式）

### 問題 1：資料結構問題

**當前實作 (v2.2)**：
```javascript
// AI 看到兩個獨立的資料結構

完整階段結構: {
  所有階段: [
    { 階段ID: 1, 階段名稱: "定標", 子階段: [
        { 子階段ID: 1, 子階段名稱: "提出研究主題", 需填寫欄位: {...} },
        { 子階段ID: 2, ... },
        { 子階段ID: 3, ... }
    ]},
    { 階段ID: 2, ... },
    { 階段ID: 3, ... }
  ]
}

最近提交記錄: {
  記錄列表: [
    { 階段: "1-3", 內容摘要: "...", 提交時間: "2025-01-10" },
    { 階段: "2-1", 內容摘要: "...", 提交時間: "2025-01-15" },
    { 階段: "2-2", 內容摘要: "...", 提交時間: "2025-01-18" }
  ]
}
```

**問題**：
- ❌ AI 需要自己解析 "1-3" 對應到哪個階段/子階段
- ❌ 看不到 1-1, 1-2 是否提交（資料不完整）
- ❌ 無法判斷提交內容的欄位完整性

**Linus 評論**：
> "Bad programmers worry about the code. Good programmers worry about data structures. 我們給了 AI 兩份獨立的資料，然後期待 AI 自己拼湊出『哪些階段完成了』。這不是 AI 的工作，這是我們應該在資料層就整合好的。"

### 問題 2：只顯示最近 5 條提交

**場景示範**：
```
學生目前在：階段 3-1

實際資料庫中的提交記錄（12 條）：
  ✅ 1-1 已提交（3 週前）
  ✅ 1-2 已提交（3 週前）
  ✅ 1-3 已提交（2 週前）
  ✅ 2-1 已提交（2 週前）
  ✅ 2-2 已提交（10 天前）
  ✅ 2-3 已提交（8 天前）
  ❌ 3-1 未提交（當前階段）

AI 實際看到的（PROMPT_SUBMISSIONS_LIMIT = 5）：
  ✅ 1-3
  ✅ 2-1
  ✅ 2-2
  ✅ 2-3
  （看不到 1-1 和 1-2）
```

**後果**：
```
學生問：「我的專案進度如何？有沒有遺漏的步驟？」

AI 無法正確回答：
❌ "階段 1 是否完整提交？"  → 看不到 1-1, 1-2，無法判斷
❌ "我是否跳過某些子階段？" → 只看到片段，無法判斷
✅ "最近幾個階段有提交"      → 這個能判斷（但不完整）
```

### 問題 3：欄位完整性不可見

**當前格式**：
```javascript
最近提交記錄: {
  記錄列表: [
    {
      階段: "1-1",
      內容摘要: "{\"提議主題\":\"環保議題\",\"主題來源\":\"新聞報...",  // ← 截斷到 200 字
      提交時間: "2025-01-10"
    }
  ]
}
```

**AI 看不到**：
- ❌ 這個子階段要求填寫哪些欄位？（5 個？10 個？）
- ❌ 學生實際填寫了哪些欄位？
- ❌ 哪些欄位遺漏了？哪些填寫不完整？

## 設計方案

### 核心設計理念

遵循 Linus Torvalds 設計哲學：
1. **資料結構優先**：設計清晰的資料結構，程式碼自然簡單
2. **消除特殊情況**：所有子階段使用統一格式，無條件分支
3. **簡單實用**：一次查詢，清晰邏輯，零複雜度
4. **零破壞性**：新增欄位，不修改現有結構

### 關鍵設計決策

#### 決策 1：全量預載 vs Function Calling

**選擇**：v2.3 使用全量預載
**理由**：
- ✅ 簡單：一次查詢，無需複雜的 Function Calling 邏輯
- ✅ 快速：並行查詢，快取機制有效
- ✅ 適合複雜分析：AI 能看到全局，做出更好建議
- ⚠️ Token 增加：預估 +1500-2000 tokens

**未來優化**：
- v2.4 可增加 Function Calling 快速路徑（針對簡單查詢）
- Phase 2 完整 Function Calling（用於執行操作）

#### 決策 2：欄位完整性檢查

**策略**：比對「需填寫欄位」與「實際提交內容」的 keys

```javascript
// 檢查邏輯（簡化版）
const requiredFields = Object.keys(subStage.userSubmit || {});
const submittedFields = Object.keys(submission.content || {});

const filled = requiredFields.filter(key =>
  submittedFields.includes(key) &&
  submission.content[key] !== null &&
  submission.content[key] !== ''
);

const missing = requiredFields.filter(key => !filled.includes(key));
```

#### 決策 3：快取策略

**保持不變**：使用現有的 `projectContextCache`
- TTL: 5 分鐘
- 自動失效：Socket 事件觸發（taskHandler, columnHandler）
- **新增**：提交事件也需要觸發快取失效

**風險等級**：低

**描述**：預估增加 1500-2000 tokens
**影響分析**：

### 風險 3：欄位完整性判斷不準確

**風險等級**：中
**描述**：比對 keys 可能無法處理複雜情況（空字串、null、空陣列）
**緩解措施**：
```javascript
// 嚴格檢查
const isFilled = (value) => {
  if (value === null || value === undefined) return false;
  if (typeof value === 'string' && value.trim() === '') return false;
  if (Array.isArray(value) && value.length === 0) return false;
  return true;
};
```

### 風險 4：階段格式不一致

**風險等級**：低
**描述**：提交記錄的 `stage` 欄位可能格式不一致（"1-1" vs "1.1" vs 數字）
**緩解措施**：

  - stages (Array of Stage IDs)

Stage:
  - id
  - name (例如: "定標")
  - processId (FK)
  - sub_stages (has many)

Sub_stage:
  - id
  - name (例如: "提出研究主題")
  - description
  - userSubmit (JSON) - 需填寫欄位定義
  - stageId (FK)
